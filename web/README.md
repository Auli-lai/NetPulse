# web/ —— Web 服务 + 前端可视化（Week 4）

把 Agent 包成 HTTP 服务，用 **SSE** 实时推送推理过程，
配一个**实时显示「用户输入 → 模型思考 → 工具调用 → 工具返回 → 最终结论」**
的单页前端。

**这是手册里 Week 4 Day 1-5 的产出物。**

---

## 一、30 秒跑起来

```bash
cd web
pip install -r requirements.txt -i https://mirrors.aliyun.com/pypi/simple/
uvicorn app:app --port 8000
```

打开 <http://127.0.0.1:8000>，点一下"演示模式"按钮，再点一个示例问题。

**演示模式不需要 API Key、不需要 C++ 服务、不需要建索引** ——
它用假模型 + 假工具把完整推理链演一遍。第一次看这个项目，从这里开始。

> 页面上有三个状态标签（工具调用 / 工具返回 / 模型思考），
> 可以单独关掉某类，只看你关心的部分。

## 二、两种跑法

### 方式一：直接跑（开发推荐）

```bash
uvicorn app:app --reload --port 8000
```

**本机开发演示就用这个。** 它和宿主机在同一个网络/IPC 命名空间，
`localhost` 的 D-Bus 直接能用，实时指标类工具可以正常工作。

### 方式二：Docker

```bash
docker compose up --build
```

打包的意义是"能一键部署到别的机器"，不是"本机开发更方便"。

⚠️ **容器里默认用不了实时指标工具。** 那需要访问宿主机的 D-Bus session bus，
而容器有独立的 IPC 命名空间，而且 session bus 的 socket 属于某个登录用户、
uid 往往对不上。挂载方法写在 `docker-compose.yml` 的注释里，但坑不少。

**好消息是这不影响服务可用** —— 依赖 D-Bus 的工具会返回错误，模型看得到并会绕开，
知识库检索和长期记忆完全不受影响。一条诊断退化成"只看历史和知识"的诊断，
仍然有价值。这是本项目一直在用的降级设计。

## 三、界面怎么用

| 元素 | 说明 |
|---|---|
| 输入框 + 诊断 | 提问，回车也可以 |
| 示例问题（胶囊） | 点一下直接问，不用打字 |
| **演示模式** | 用假模型 + 假工具，零配置可跑。开着的时候按钮会高亮 |
| 主题（自动/浅色/深色） | 跟随系统或手动切换 |
| 状态行 | 就绪 / 正在诊断 / 完成 / 失败。连接中断时会自动重连 |
| 过滤行 | 单独关掉「工具调用 / 工具返回 / 模型思考」 |
| KPI 行 | 推理轮次、工具调用次数、耗时、工具报错数、被拦截的重复调用数 |
| 时间线 | 每一轮的思考、每一次工具调用（参数 + 返回，可展开）、最终结论 |

**首次打开时**，页面会调 `/api/health` 探一下环境，缺什么直接提示
（"没配 API Key · 没建检索索引 · C++ 服务没在跑"），并给一个一键打开演示模式的按钮。
不用等你点了诊断才发现报错。

### 几个值得盯的地方

- **`被拦截的重复调用`** 这个 KPI。它不是 0 的时候，说明模型的容错机制真的在工作了
  —— 时间线上那条会被标成 ⛔「已拦截」。这是**唯一能直观看到容错生效的地方**，
  演示时可以专门讲这一条。
- **工具返回可以展开**。里面是 D-Bus / FAISS 返回的原始 JSON，
  能看出模型是基于什么数据下的结论。
- **结束原因**。命令行版的输出里有；Web 版在 `done` 事件里。
  如果是 `max_rounds` 或 `llm_error`，结论的可信度要打折。

## 四、接口

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/` | 前端页面 |
| GET | `/api/health` | 健康检查 + 各依赖状态 |
| GET | `/api/tools` | 7 个工具及 schema |
| POST | `/api/diagnose` | 发起诊断 → `{run_id, stream}` |
| GET | `/api/diagnose/{id}/stream` | **SSE 事件流** |
| GET | `/api/diagnose/{id}` | 取最终结果（轮询兜底） |
| GET | `/api/runs` | 最近的运行列表 |
| GET | `/api/memories` | 长期记忆列表 |

### SSE 事件类型

前端按事件名分发（`addEventListener('tool_result', ...)`），不用在回调里 switch。

| 事件 | 什么时候发 | 主要字段 |
|---|---|---|
| `start` | 开始 | `question` |
| `thought` | 模型每一轮的思考 | `round`, `text` |
| `assistant` | 模型要求调工具 | `round`, `tool_calls` |
| `tool_result` | 每个工具执行完 | `name`, `arguments`, `raw`, `is_error`, `intervention`, `elapsed_ms` |
| `memory_recall` | 召回了长期记忆 | `count`, `items` |
| `forcing_conclusion` | 达到上限强制收尾 | — |
| `final` | 最终结论 | `text` |
| `finish` | 诊断结束 | `stopped_because`, `rounds` |
| `done` | **流结束**（前端据此收工） | `run_id`, `elapsed_ms`, `error` |
| `error` | 出错 | `message` |

用 curl 调试：

```bash

python -c "import io,json; io.open('q.json','w',encoding='utf-8').write(json.dumps({'question':'网络很卡','demo':True}, ensure_ascii=False))"
```

## 五、两个核心设计

### ① 同步的 Agent 和异步的 Web 之间那座桥

Agent 循环是**同步阻塞**的（调模型等几秒、调工具等几百毫秒），
一次诊断可能跑 30~60 秒。而 FastAPI 跑在 asyncio 事件循环上。

**如果在路由里直接 `await agent.run()`，整个事件循环会被卡死** ——
不是"慢"，是"服务不可用"，连你自己的 SSE 连接都建立不起来。

所以 Agent 被扔到工作线程里跑，事件通过线程安全的方式送回事件循环：

```
asyncio 事件循环                      工作线程
──────────────────                   ────────────────
接收请求
  └─ asyncio.to_thread ────────────►  agent.run()  （阻塞 30~60s）
                                          │ on_event 回调
  订阅者队列  ◄── call_soon_threadsafe ───┘
```

`call_soon_threadsafe` 是**必须**的。`asyncio.Queue` 不是线程安全的，
从别的线程直接 `put_nowait` 在单线程测试里"看起来能跑"，
真实并发下会丢事件 —— 而且它不会立刻报错，是最难查的那类 bug。

`test_api.py` 里专门有一个 `test_thread_bridge` 测这条路径。

### ② SSE 断点续传 —— 让 EventSource 的自动重连变成好事

浏览器的 `EventSource` **断线后会自动重连**。如果服务端把事件当成一次性流：

```
连接断了 → 浏览器自动重连 → 服务端又跑一次诊断 → 又断 → 又重连 → 无限烧钱
```

所以 Run 保存了**完整的事件历史**，订阅时可以从指定序号续发：

```
连接断了 → 重连（浏览器自动带 Last-Event-ID）→ 从断点继续 → 无缝衔接
```

**这是 SSE 相比 WebSocket 少有人用的一个优势**：断点续传是协议内置的
（每条消息带 `id:` 字段，重连时浏览器自动放进 `Last-Event-ID` 请求头），
不用自己实现。

顺带这也解释了为什么接口是"先 POST 再订阅"而不是一个 GET 拉到底：

- `EventSource` **只支持 GET，不能 POST**，问题文本只能塞 URL
- 而那个 URL 每次自动重连都会**重新发起一次诊断**

细节写在 `runstore.py` 的模块注释里。

## 六、视觉设计说明

前端是单文件、**零外部依赖**（连 favicon 都是内联的 data URI），
断网也能完整显示。配色不是随手挑的：

- **状态色**（成功 `#0ca30c` / 警告 `#fab219` / 失败 `#d03b3b`）取自一套固定状态色板，
  **不做主题化** —— 语义色换主题会让人认不出来
- **两条硬规则**：
  1. **状态永远不只靠颜色表达** —— 每个标记旁边都有图标（`🔧 ❌ ⛔`）和文字标签
     （成功 / 失败 / 已拦截）。红绿对色盲用户不可分，颜色只是加速识别
  2. 低对比度的状态色（警告色在浅色背景上只有 1.79:1）**只当标记和边框用**，
     文字一律用文字色 —— 保证可读性
- **深色模式是单独选的一套色阶**，不是把浅色反一下
- 配色改动前跑过校验脚本，确认相邻色的色盲可分辨度达标

这些不是洁癖：一个诊断界面上"哪条失败了"是**关键信息**，
如果它只能靠颜色传达，色觉障碍用户就用不了这个工具。

## 七、测试

```bash
python test_api.py          # 54 项，全离线（TestClient + 假 Agent）
python _screenshot.py       # 真实浏览器渲染 + 截图 + 断言
```

### 为什么不止"把接口点一遍"

`test_api.py` 重点测的是**正常路径下看不出来**的三类问题：

1. **线程桥接** —— 直接 `put_nowait` 在单线程测试里也能过，只在并发下丢事件
2. **SSE 断点续传** —— 不模拟重连就永远发现不了"重连=重跑=重复烧钱"
3. **失败也要有终点** —— 诊断抛异常时前端必须收到 `done`，否则一直转圈

`_screenshot.py` 更进一步：它开一个**真实浏览器**（用系统自带的 Edge/Chrome，
不需要 `playwright install` 下载），跑一次完整诊断，然后：

- 检查有没有 JS 运行时异常（语法检查抓不到的那类）
- 检查 KPI 数值、结论是否真的渲染出来、有没有横向溢出
- 浅色/深色各截一张图

**这个脚本抓到过一个真 bug**：KPI 上"推理轮次"显示 0，
而时间线上明明画了 5 轮思考 —— 因为计数器 `roundNo++` 加的是一个没人读的变量。
`node --check` 和 DOM 结构检查都发现不了它，只有把页面渲染出来看才行。

> 面试可以这么讲："我给前端写了个自动化的视觉检查 —— 起真浏览器、跑完整流程、
> 断言 KPI 数值和渲染结果。它抓到了一个语法检查和单元测试都发现不了的 bug：
> 页面上画了 5 轮思考，KPI 却显示 0，因为计数加错了变量。
> **这类'看起来对但其实错了'的问题，只有真的渲染出来才看得见。**"

## 八、已知缺口

### ⚠️ 没有鉴权 —— 这是最要紧的一条

服务**默认只绑 `127.0.0.1`**。不要直接改成 `0.0.0.0` 暴露到公网：

- 任何人都能发起诊断 = **消耗你的 API 额度**
- `netpulse://logs/{name}` 能读日志文件
- `/api/memories` 会暴露你的历史诊断记录

要对外暴露必须先加认证（至少一个 Bearer token），并且限制 `MAX_SESSIONS` 和
请求频率。目前这些都没做。

### 其他

| 缺口 | 说明 |
|---|---|
| 前端没做分页 | 运行列表最多 50 条，没有翻页 |
| 会话存在内存里 | 重启服务后 `session_id` 全部失效（长期记忆不受影响，它是落盘的） |
| 没有流式输出结论 | 结论是一次性出来的，不是逐字打出来的。要做的话得换 streaming API |
| SSE 没有心跳 | 中间有反向代理且空闲太久时可能被断开。靠自动重连兜住了，但没主动发心跳 |
| 截图脚本依赖系统浏览器 | 只测了 Windows 的 Edge；Linux 上改 `_pick_channel()` 里的路径 |
